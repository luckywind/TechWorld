# 📘 Paseo 核心概念与实战指南

# 一、 核心概念解析（基石）

理解 Paseo 的关键在于区分“逻辑调度”与“物理执行”。

1. **Project（项目）**：宏观的业务目标或逻辑分组（如“重构认证系统”），定义了全局配置和共享资源。
2. **Workspace（工作区）**：AI Agent 运行时的**逻辑会话和上下文环境**。它就像一个独立的工作台，拥有独立的对话历史。
3. **Worktree（工作树）**：Git 的**物理隔离机制**。开启后，Paseo 会在底层创建一个独立的隐藏文件夹（基于新分支），让 AI 在沙盒中修改代码，保护主分支绝对安全。
4. **Provider（提供商）**：提供大模型 API 的服务方（如 Claude, Codex）。相当于你雇佣的不同特长的“施工队”。

# 二、 核心机制与常见疑问解答

### 1. 关于目录共享与隔离
*   **疑问：新建 Workspace 没让填路径，多个 Workspace 会共享文件夹吗？**
    *   **解答**：**是的，默认共享。** 它们都指向 Project 的根目录。这种设计是为了方便多个 Agent 协作，共享项目的全局配置文件（如 `package.json`）。
*   **疑问：既然共享，为什么还要建多个 Workspace？**
    *   **解答**：为了实现 **①并行执行**（提升效率）、**②故障隔离**（一个搞崩不影响另一个）、**③上下文管理**（拆分任务防 AI 遗忘）、**④职责分离**。
*   **疑问：如果怕冲突怎么办？**
    *   **解答**：如果任务互不干扰，共享文件夹最高效。如果需要极端隔离，在创建时手动开启 **Worktree** 开关，Paseo 会自动创建物理隔离的沙盒。

### 2. 关于客户端 UI 操作
*   **疑问：使用客户端 UI 可以完成所有操作吗？**
    *   **解答**：**完全可以，且是官方最推荐的方式。** UI 支持点击 `+` 新建会话、下拉菜单切换 Provider、在“高级设置”中一键开启 Worktree，并提供比命令行更友好的实时监控和代码 Diff 对比。
*   **疑问：右上角的分屏按钮怎么不显示？**
    *   **解答**：分屏需要“至少两个内容”。你需要**先新建第二个 Workspace（标签页）**，该按钮就会亮起；或者它被折叠在了右上角的 **`...` (更多选项)** 菜单中。
*   **疑问：同一个 Workspace 下为什么还能加 Agent, Terminal, Diff, 浏览器？**
    *   **解答**：因为 Workspace 被设计为 **“全功能工作台”**。它们共享同一个任务上下文（文件夹）：Agent 负责思考，Terminal 负责执行命令，Diff 负责审查代码变动，浏览器负责预览效果。这形成了一个完美的闭环，让你无需在多个软件间频繁切换。

# 三、 实战场景与最佳实践（SOP）

### 场景一：开发新功能 / 大重构（高风险）
*   **策略**：安全隔离模式
*   **步骤**：
    1. 新建 Workspace 时，**务必开启 Worktree**（如命名 `feature-xxx`）。
    2. 在 Agent 中下达详细、结构化的需求指令。
    3. AI 完成后，切换到 **Diff** 标签页，逐行审查代码变动。
    4. 确认无误后，在 Terminal 中执行 `git merge` 合入主分支；若有误，直接在 Agent 中指出让其重写。

### 场景二：日常修 Bug / 小优化（低风险）
*   **策略**：高效共享模式
*   **步骤**：
    1. 直接在当前目录新建 Workspace，**不开启 Worktree**（共享文件夹）。
    2. 让 AI 修复 Bug，并密切关注 **Terminal** 标签页的输出。
    3. 如果终端报错，直接在 Agent 中反馈：“终端报错了，缺少 XXX，请处理”，AI 会读取报错并自动修正。
    4. 若是前端改动，直接点开 **浏览器** 标签验证效果。

### 场景三：复杂任务 / 技术攻关（高复杂度）
*   **策略**：多 Agent 协作模式
*   **步骤**：
    1. **拆分任务**：不要指望一个 AI 干完所有事。
    2. **搭配 Provider**：Workspace A 使用 **Claude** 进行架构规划和逻辑推理；Workspace B 使用 **Codex** 进行具体的代码实现和测试编写。
    3. **并行推进**：同时开启多个 Workspace，分别处理后端 API、前端页面和数据库脚本。

# 四、 进阶策略：单 Provider 下的职责拆分

**核心结论**：即使你只有一个 Provider（比如只有 Codex），在复杂任务中**依然强烈建议拆分职责（使用多个 Workspace）**。

**原因如下**：
1.  **突破“上下文遗忘”瓶颈**：单会话过长会导致 AI 遗忘早期细节。拆分 Workspace 能提供干净的上下文。
2.  **实现真正的“并行处理”**：开 3 个 Workspace 相当于让模型“分身”成 3 个，整体开发时间直接缩短。
3.  **提供“容错机制”**：如果某个 Workspace 里的 AI 陷入死循环（降智），直接关闭并新建一个干净的 Workspace 即可，无需清理污染的记忆。
4.  **保持“角色设定”专注**：可以在不同 Workspace 给予不同的初始指令（如一个扮演严谨的后端，一个扮演挑剔的测试）。

# 六、 新手避坑与高阶心法

1.  **保持上下文干净**：如果一个 Workspace 的对话轮数过多（如超过 20 轮），AI 容易“遗忘”或逻辑混乱。此时应**总结当前进度，新建一个 Workspace 重新开始**。
2.  **警惕 Terminal 的“暴力操作”**：AI 有时为了强行完成任务，可能会在终端执行危险命令。偶尔扫一眼 Terminal，确保其行为符合预期。
3.  **善用“手动干预”**：AI 卡住时不要死等。你可以直接在 Paseo 的 Terminal 里手动敲命令解决问题，然后告诉 Agent：“我刚才手动修了 XXX，你基于此继续”。
4.  **黄金法则**：**大胆使用，小心审查。** 用 Worktree 保护底线，用 Diff 把控质量，用 Terminal 和浏览器加速验证。
